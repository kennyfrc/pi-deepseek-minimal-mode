# pi-deepseek-minimal-mode

The DeepSeek Harness `minimal` preset for Pi, ported 1:1 at the wire level,
plus Claude Code-style tool search as the only sanctioned delta.

For DeepSeek-family models the provider payload IS the harness minimal
request:

- **system**: `You are a helpful software engineer assistant.` — the preset
  persona, complete; nothing else.
- **tools**: exactly two entries — `[bash, str_replace_editor]`, pi's LIVE
  wire entries preserved verbatim (open schema: the model can use
  `timeout`/`background`/`job`/`action` and the editor's pi notes). The frozen
  harness pair is the fallback and the A/B reference
  (`PI_MINIMAL_WIRE_VARIANT=harness`). Verified live: the caveman register
  is identical under either pair — only the system slot matters.
- **request params**: only what the harness serializer emits; pi-only extras
  (`store`, `max_completion_tokens`, `reasoning_effort`) are dropped.

Ground truth: the harness requestHeader dump (fixture-embedded in
`test/harness-payload.test.ts`). `before_provider_request` projects every
request onto it; the reference test asserts byte-equality.

`tool_search` is never injected in the `tools` parameter. Nothing advertises
it: the model calls it by name if it ever emits the call (its calls route
through the active set, where the runtime can execute them). A
natural-language query is ranked with BM25 over tool names (boosted) and
descriptions — the same mechanic as Claude Code's
`tool_search_tool_bm25` — and the top matches are returned with one-line
descriptions and their argument shapes, and ACTIVATED: the model then calls
them by name too, still without their definitions ever entering the payload.
Only what gets used costs context; the payload stays at two tools forever.

## Why

- DSH minimal mode strips environment interference: DeepSeek models drift
  with many tools, and every tool definition is payload on every request
  (prefill on Chinese models is slow and cached-prefix-sensitive).
- Claude Code's tool search exists because tool definitions eat the context
  window (50 tools ≈ 10-20K tokens) and selection accuracy degrades past
  30-50 tools. "Keep your 3-5 most frequently used tools non-deferred" —
  here those are bash + str_replace_editor + tool_search.
- The two-tool surface plus the bare persona IS the guidance. An injected
  contract prompt or skill digest breaks the anchor (community repro: 0/9
  with a digest present), so none is sent. tool_search is available to a
  model that emits it by name, and never shipped as a tool definition.

## The reminder

Two durable (session:start) reminders coexist, both delivered by
pi-system-reminders. Each is PERSISTED once as a hidden session message
placed immediately before the session's FIRST user prompt — wrapped in the
same `system_reminder` envelope the transient channel uses, serialized to a
user-role message on the wire, each inner `<reminder>` tag marked
`durable="true"`. Because the block lives in the session transcript it
replays in EVERY subsequent request and on resume: nothing re-fires,
nothing accumulates, and the AGENTS.md/skills context is never dropped in
later prompts. Branching to a point before the block re-derives and
re-sends it once on that branch.

- **agents-md**: the context files pi loaded (AGENTS.md et al.), followed
  by the available-skills catalog. Placement matters: system-prompt
  injection of this content flips DeepSeek's thinking register to full
  grammar; user-message injection keeps the RL caveman register
  (A/B-verified against api.deepseek.com, re-verified live with the skills
  block present). Non-minimal models get these files through the normal
  system prompt, so the reminder stays silent for them.

  The skills catalog is pi's standard protocol block (the same
  `<available_skills>` text the system prompt would carry, generated by
  pi's own loader + formatter: name, one-line description, SKILL.md
  location, with `disableModelInvocation` skills excluded). It is appended
  because tool_search indexes TOOLS only — skills are not tools — so
  without this block the model can never discover a skill in minimal mode.
  The block keeps the same user-message placement as the files (never the
  system prompt), which is what preserves the register. Escape hatch:
  `PI_MINIMAL_SKILLS=0` drops just the skills catalog
  (`PI_MINIMAL_AGENTS_MD=0` drops the whole reminder).
- **tool-search**: a one-shot nudge to search for an existing tool with
  tool_search before improvising with bash. Durable — sent once before the
  first prompt and replayed from the transcript thereafter; the per-turn
  transient variant was removed because re-injected prompt text breaks the
  anchor (community repro: 0/9 with a skill digest present).

Durable content never competes in the transient eviction budget, so a full
AGENTS.md plus the skills catalog fits. Every OTHER extension's reminder
traffic (flows, memo, third-party skill-catalog reminders) is stripped
from the wire for minimal sessions: the payload carries only the persisted
durable pair, wherever it appears in the message history.

## How tool_search works

1. The model calls `tool_search` by name. Nothing advertises it every turn;
   the durable session:start nudge above points at it exactly once. The call
   routes through the active set even though the tool is not in the payload.
2. BM25 ranks the full registered catalog (names boosted, one-line
   descriptions, stopwords dropped, default limit 5, max 20).
3. Matches are returned as `- name: one-line description` plus a compact
   `args: ...` shape, with a note to call them by name on the next step.
4. The matched tools are appended to the active set (append-only for the
   session) so they are callable by name; they survive the gate's sweeps and
   never enter the provider payload (before_provider_request strips them).

The always-available tools (`bash`, `str_replace_editor`, `tool_search`) are
never returned as matches. There is no kimi-interface `WebSearch` wrapper:
pi already ships `web_search` and `web_fetch`, and tool_search surfaces them
on demand — a second search tool would only duplicate the surface and burn
context.

## Configuration

`~/.pi/agent/pi-deepseek-minimal-mode.json`:

```json
{
  "mode": "auto",
  "deepseekPatterns": ["deepseek"],
  "whitelist": []
}
```

- `mode`: `auto` (default, deepseek only) | `on` (every model) | `off` (inert).
- `deepseekPatterns`: regex list tested against model id/provider/name.
- `whitelist`: extra tool names always visible in minimal mode.

## Dependencies

- **pi-str-replace-editor** (hard): registers the `str_replace_editor` tool
  the minimal contract is built on; without it, deepseek sessions advertise a
  tool that cannot execute. Listed in `dependencies`.
- **pi-system-reminders** (hard): the durable-reminder channel for the
  one-shot AGENTS.md delivery. Listed in `dependencies`.
- pi's bundled cores (`@earendil-works/*`, `typebox`) resolve as peers.

## Coexistence

- pi-str-replace-editor owns `{read, edit, write, grep, find, ls,
  str_replace_editor}` and its block messages; this gate never blocks those
  names, only removes them from the active set for minimal models.
- Both gates compute their desired set from the current active set, so they
  converge in any load order. Load pi-deepseek-minimal-mode after
  pi-str-replace-editor for the tightest set on deepseek.
- pi's tool-refresh machinery re-adds late-registered tools (e.g. the MCP
  adapter's gateway) with no event; the gate re-applies at `turn_start` and
  `context`, and `before_provider_request` projects the wire payload onto
  the harness reference, which removes any such tool from the request no
  matter how it got into the active set.
- Instrument the live wire payload with `PI_MINIMAL_MODE_DUMP=<path> pi ...`;
  it writes the final projected request (post-projection) as JSON.
- Variant hook: `PI_MINIMAL_WIRE_VARIANT=harness` swaps pi's live wire
  entries for the frozen RL fixture pair (persona/wire params unchanged).
  Verified 08-16 both ways: the caveman register is identical — the system
  slot (persona) is the only register lever. Live entries are the default
  (full pi surface, no stale claims like the harness description's
  "state is persistent" / "no internet", which are false on pi's executor).

## Development

```bash
npm run check:minimal-mode   # typecheck
npm run test:minimal-mode    # gate + tool-search + harness-payload + wiring tests
```

## Quick start

```bash
pi install npm:@kennyfrc/pi-deepseek-minimal-mode
```

That writes the package into `~/.pi/agent/settings.json` and resolves its
dependencies automatically. Try it once without installing:

```bash
pi -e npm:@kennyfrc/pi-deepseek-minimal-mode
```

Or register it by hand in `~/.pi/agent/settings.json`:

```json
{ "packages": ["@kennyfrc/pi-deepseek-minimal-mode"] }
```

Restart pi (or start a new session) to load it.
